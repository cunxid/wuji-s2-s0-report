Skills through the depth-based motion planner, in the co-simulation — first runs

What this is and is not. The new skill layer (s2/dexharness/cap, organised the way ASPIRE organises its harness: a registry of typed tools, a sandbox for the agent's program, one template every skill goes through) ran for the first time in the real co-simulation on 2026-11-24. These runs have no tracking policy and an empty hand: they show that a skill observes, plans against what the depth images show, and that the arm then follows the plan. Nothing is grasped and no task is attempted here.

How every skill runs

  1. The skill is given the current observation: depth images from the scene cameras and the measured joint angles. An observation from before the arm last moved is refused.
  2. The depth images are turned into a collision model of the scene (voxels merged into boxes); the robot's own pixels are removed.
  3. One motion plan is made for the Tianji arm against that model: every row is a joint configuration found by inverse kinematics and checked for collision; a lift is a straight Cartesian line only if every sample of the line is solvable and collision-free, otherwise it is refused or planned around.
  4. Exactly that plan is executed: the simulator's arm servo follows the planned joint rows; a trajectory that was not issued by the planner, or was changed afterwards, is refused.
  5. The result is checked from joint measurements and a fresh observation.

Each clip below has three panels: (1) the depth image the skill was given, with the robot's own pixels in blue and the planned palm path in green; (2) the plan: the robot alone moving through the boxes built from that depth; (3) the execution re-drawn from the recorded joints in the true scene, planned path green, executed path orange.

What ran: 12 executed skill calls on two scenes

In these 12 calls the flight record holds 0 contact rows between the robot and the scene or itself; the palm followed the plan with a mean error of 0.89 to 1.21 mm (largest 4.36 mm); planning took 0.24 to 0.69 s per call on a loaded machine. Lifts and retreats were planned as Cartesian lines (planner mode cartesian_line), the other moves in joint space (direct).

Refusals

A goal that cannot be reached or would collide returns a typed error and no trajectory; the arm does not move.

What is still wrong

Found in the same session by probing beyond the simple moves (full list with reproductions: s2/outputs/skills_dev/cosim_scout/REPORT.md). None of this is fixed yet.
  1. A move that also commands a hand posture is collision-checked with the hand as it was before the move (clip above).
  2. The scripted postures "fist" and "point" count as a self collision in the planner's model (little finger 4 mm inside the wrist flange); after one of them no plan is accepted, so the skills that press and push cannot plan yet.
  3. Planning time is not charged to the episode in the co-simulation: every execution was charged 1 tick, while the measured planning interval was 23 to 114 ticks. The design says planning time is paid for in held ticks.
  4. The clip footers print "planned clearance 20.0 mm", which is the planner's measuring cap, not a measurement, and the "executed clearance" ignores finger contacts.
  5. A refused plan shows the start configuration instead of the offending one.
  6. A program that calls the plan tool directly leaves a run folder the video builder rejects.

Not done yet

  • No run with the tracking policy: no grasp, transport, place, press, push or strike through this layer.
  • Perception names objects by the nearest training-set shape (the tennis ball is called a 60 mm box); object identity is not established.
  • Only the right arm was driven. The left arm stayed parked.
  • Simulated depth is exact; sensor noise is not modelled.
